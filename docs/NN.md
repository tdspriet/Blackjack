# ONE Blackjack Lab — the neural network

Everything about the network that plays ONE Blackjack: what it sees, how it is trained and why, how good it is,
what it learned, and how to retrain or improve it. Code: `backend/onebj/ai/`. Interface for the server/frontend:
`docs/SPEC.md` §5.1. Notebook: `notebooks/nn_playground.ipynb`.

## 1. What the network is

```
input (61) ── trunk.0 (128, ReLU) ── trunk.1 (64, ReLU) ──┬── play  Q(stand, hit, double, split) + cashout (wired)
                                                           └── bet   EV(main, PP, 21+3, Crazy 7, Bust Bonus, insurance)
```

One network, one input layer, two heads — so the whole agent fits in the NN panel's graph. ~17k parameters.

| decision | input context | output used | rule |
|---|---|---|---|
| play | hand + dealer + shoe features | `play` head | argmax over legal actions of Q (EV per unit of the hand's original bet) |
| insurance | 2-card hand + dealer ace + shoe | `bet[insurance]` | insure if predicted EV per unit insurance stake > 0 |
| bets | shoe features only (`phase_bet` = 1) | `bet` head | main: ½-Kelly on predicted edge, clamped to [1, 12] units; side bet at the €1 minimum if predicted EV > 2 % |

**The cash-out output is not learned.** Its value is known exactly (`offer / bet − 1`), so it is wired from the
`cashout_value` input straight to the output. The network only has to learn whether holding is worth more — which
turned out to be the most valuable thing it learns (§4).

### 1.1 Features (`features.py`)

| group | features | encoding |
|---|---|---|
| hand | `player_total`, `total_4`…`total_21`, `soft`, `num_cards`, `pair_A`…`pair_T`, `can_double`, `can_split`, `is_split`, `cashout_value` | total/21 plus one-hot; num_cards/6 (Six Card Charlie!); one-hot of a *splittable* pair; exact cash-out EV |
| dealer | `dealer_up_A`…`dealer_up_T` | one-hot |
| composition | `unseen_A`…`unseen_T` | relative richness of the unseen cards per rank, `(share/expected − 1) × 2.5`, clipped to ±2 — per rank, so the 7s (Crazy 7), 5s, aces… each have their own input |
| count / shoe | `hilo_tc`, `decks_unseen`, `shoe_half2`, `cards_to_cut` | TC/6, decks/8, 0/1, cards before the cut card / 208 |
| context | `phase_bet`, `phase_ins` | which decision is asked |

Only legal information: everything comes from `Observation` (or the same public table state on the fast path —
`test_obs_and_table_paths_agree` checks bit-identical vectors, `test_features_never_see_the_hole_card` checks that
resampling the hidden cards changes nothing). "Unseen" = 416 − seen over the whole 8-deck shoe, so the count carries
over the half switch as SPEC §1.1 requires. The feature set is versioned (`FeatureSpec`) and stored in checkpoints.

## 2. How it is trained (`train.py`, `datagen.py`)

Generalised policy iteration in *generations*:

```
for g in 0..G-1:
    data:  play rounds with the current policy (basic strategy for g=0, then the network) + 10 % random actions,
           on deliberately skewed shoes; label every decision state (4M / 3M / 3M), 1.5M pre-deal states and every
           insurance spot
    fit:   warm-started Adam on all data so far (cosine LR cycle, peak halves every generation)
    eval:  paired flat-bet comparison vs basic strategy (1M rounds) + solver-regret benchmark → training log
```

### 2.1 Play-head targets — and why not plain Monte Carlo

The obvious target is the all-action Monte-Carlo return: for each state, `table.clone(resample_unseen=True)` (every
unseen card, hole card included, reshuffled → no leak), apply every legal action to a copy of the same clone
(common random numbers) and finish the round with the current policy. This is implemented (`targets: "mc"`) and
correct, but it is **too noisy for this game**. A single return has σ ≈ 0.8–1.5 units, while the decisions that
matter most here — *cash out or keep playing* — are decided by margins of 0.005–0.02 (§4.2). At equal data
(1.5M states) the MC-trained net reached a regret of 0.0038 per decision vs 0.0008 for the alternative below, and
still cashed out far too often (27 % of decisions, losing 0.002 per cash-out vs holding: exactly the bug seen in an
early `nn:med` checkpoint — soft 17 v A cashed out at TC 0 because Q(hit) was ~0.1 too pessimistic).

So the play head is trained by **distilling a planner** (`targets: "solver"`, the default in every generation):
the target for each visited state is the EV of every action from dynamic programming on the *current unseen
composition* — the engine's infinite-deck solver (`strategy/solver.py`, the machinery that derives basic strategy,
the Hi-Lo indices and the cash-out values), extended in `ai/oracle.py` (`CashSolver`) with the cash-out option at
every later decision (after a hit, and on each split hand). Noise-free targets at ~0.1 ms per state. Generations 1
and 2 add data from the *network's own* state distribution (its behaviour policy) and on-policy bet-head targets.

Engine rollouts can be mixed in (`targets: "blend"`: target = solver + `mc_weight` × (MC − solver), continuation =
the network's policy), to correct the solver's approximations (with-replacement draws at a fixed composition, no
crowd, total-dependent continuation) with unbiased engine ground truth. Measured, with everything else equal:

| schedule (3 generations, same seed and data sizes) | regret / decision | paired gain vs basic (1M rounds, same cards) |
|---|---|---|
| solver, solver, solver (**default**) | 0.00036 | +0.693 % |
| solver, blend 0.25, blend 0.25 | 0.00060 | +0.636 % |
| head-to-head on 4M fresh paired rounds | | solver schedule **+0.020 % ± 0.012 %** better |

At this data budget the rollout noise costs more than the solver's bias, so the blend stays an option (and the
pure-MC path a reference implementation) rather than the default. The engine remains the judge: every evaluation
number in this document is measured by playing the real engine, never by the solver.

Why this is still "learning": the network never sees the solver at play time. It compresses a fresh DP per
composition into a 17k-parameter function of 61 features that answers in ~10 µs and generalises to states and
compositions it never saw; and the bet head, the insurance output and all evaluation come from realised engine
outcomes. The training log tracks both views: **regret vs the solver** (how well it imitates the planner) and the
**paired engine EV** (ground truth).

### 2.2 Bet-head targets

* **main**: realised main-bet return per unit of 4 resampled full rounds per pre-deal state, played by the current
  policy (insurance declined). Under the *learned* policy from generation 1 on — the bet head learns that the
  network's play (with cash-outs) is worth more than basic strategy.
* **Perfect Pairs, 21+3, Crazy 7, insurance**: realised outcomes of a *deal Monte Carlo* — 2 random permutations
  of the unseen pool cut into 5-card deals (P1, up, P2, hole, next card), settled with the engine's own `settle_*`
  functions (tabulated once). That is ~120–160 realised deals per state: same expectation as playing the rounds,
  2–3 orders of magnitude less variance (Crazy 7 has σ ≈ 11 per unit!).
* **Bust Bonus**: realised from the 4 full rounds (it depends on everyone's draws).
* **insurance** at the insurance decision: 8 resampled hole cards per spot.
* Loss: MSE per output standardised by the target's std (`bet_scale`), masked so play rows only train the play head
  and insurance rows only the insurance output.

### 2.3 State coverage

* ε = 10 % random legal actions reach rare hands (soft 18 with 4 cards, hard 16 with 5 cards, odd splits).
* **Tilted shuffles**: half of the shoes get a biased shuffle (sort key = uniform + α·direction[rank], direction =
  Hi-Lo tags, a random direction, or the 7s with ×2.5 weight; |α| ≤ 0.08). True counts reach ±9 at the 1st/99th
  percentile (±5.7 natural) and 7-rich shoes become common. Because every target is computed on *resampled* clones,
  the tilt only changes which states are visited, never their labels — this is exactly what
  `clone(resample_unseen=True)` is for.
* 10M play states, 4.5M bet states and ~0.6M insurance spots in the default run.

### 2.4 Reproducibility

Everything is seeded (`--seed`, default 1). Data generation is split into a fixed number of chunks (`chunks: 40`)
independent of the worker count, so the same config gives the same data on any machine; on the same machine and
thread count the weights are identical too. `checkpoints/<name>.json` stores the config hash, the full training
config, the generator config, the game config, the feature names, per-generation data sizes and timings, and the
training log.

Wall-clock of the default run (M4, 10 cores): data generation 4.1 min per generation (solver targets ~0.1 ms
per play state; bet states ~0.5 ms with 4 full rounds each), fitting 26 / 20 / 34 s (CPU, batch 4096, ~1.3 ms
per step), evaluation ~10 s per generation, plus the regret benchmark; total **14.2 min**. Pure Monte-Carlo or blend targets cost
~1.5–2× more data-generation time per state.

## 3. Bet sizing and side bets

* Main: `stake = 0.5 × edge / 1.33 × bankroll` (half Kelly; 1.33 = variance per unit of the main bet incl.
  doubles/splits), rounded to whole euros and clamped to `[unit, 12 × unit]`. Defaults: unit €1 (the table minimum,
  same as the Hi-Lo baseline's ramp), bankroll €1000 fixed (`bankroll_mode: "live"` uses the current balance).
  Note what Kelly implies: with a €10 unit and €1000 the Kelly stake at a +1 % edge is €3.76, i.e. below the unit
  — a 1–12 spread needs ~1000 units of bankroll.
* Side bets: placed at the €1 minimum when the predicted EV > 2 % (a margin for model error). Kelly would bet less:
  Crazy 7 has a variance of ≈ 200 per unit, so at its typical +20 % EV the *full*-Kelly stake on €1000 is €1.00 and
  half Kelly €0.50 — the €1 table minimum already over-bets Kelly. A small, very high-variance edge; see §5.

## 4. What it learned

### 4.1 Play: count-dependent strategy

Solver regret on 60,000 natural decision states (basic strategy + 10 % exploration): **0.00032 per decision for the
network vs 0.00568 for basic strategy** (the solver itself = 0); the network picks the solver-optimal action in
95.3 % of states (basic strategy: 77.9 %); Q-value RMSE vs the solver 0.0075, bias +0.0007.

Index plays it discovered on its own (true count where it switches, 3 decks unseen, Hi-Lo-shifted composition; the
Hi-Lo column is the engine's Illustrious-18 table):

| play | Hi-Lo | NN | | play | Hi-Lo | NN |
|---|---|---|---|---|---|---|
| insurance | +3 | +4.0 | | 11 v A double | +2 | +1.9 |
| 16 v T stand | 0 | +0.1 | | 9 v 2 double | +1 | +1.1 |
| 15 v T stand | +4 | +5.4 | | 10 v A double | +4 | +4.3 |
| T,T v 5 split | +5 | +5.2 | | 9 v 7 double | +3 | +4.0 |
| T,T v 6 split | +4 | +4.3 | | 16 v 9 stand | +5 | +4.7 |
| 11 v T double | +3 | never¹ | | 13 v 2 hit below | −1 | −1.1 |
| 12 v 3 stand | +1 | +1.2 | | 12 v 4 hit below | 0 | 0.0 |
| 12 v 2 stand | +3 | +2.7 | | 12 v 5 hit below | −2 | −1.3 |
| | | | | 12 v 6 hit below | −1 | −1.0 |
| | | | | 13 v 3 hit below | −2 | −2.2 |

¹ Not a mistake: hitting 11 v T keeps the cash-out option for the next decision (11 + small card = a stiff vs T
in a ten-rich shoe, which is then cashed out), and doubling forfeits it. The cash-aware solver agrees (TC +4: hit
+0.063, double +0.055); without later cash-outs the plain solver doubles from TC ≈ +3.5, and the network, playing
the no-cash-out ablation, does double 11 v T in ten-rich compositions.

So yes: it **stands 16 v T at TC ≥ 0**, **insures at TC ≥ +4** (exact break-even for this composition model is
+3.3, the head is ~0.01 EV pessimistic there), and **doubles 10 v A at TC ≥ +4.3**. The most frequent deviations in
play (no cash-out): 16 v T stand (also with 3–4 cards — Charlie-aware), 12 v 4/5/6 and 13 v 2/3 hit at negative
counts, 11 v T double and 12 v 2/3 stand at positive counts. Charts at TC −3 / 0 / +3: `docs/nn_eval.md` and the
notebook.

### 4.2 The cash-out option is the network's biggest play edge

The cash-out offer is `0.98 × fair value`, where the fair value is the hand's EV (stake included) for a **fresh**
shoe. The 2 % haircut is taken on `1 + EV`, so it is tiny for bad hands (16 v T: 0.0085 units) and larger for good
ones (11 v 6: 0.033). Any composition that makes *this hand* worse than in a fresh shoe by more than the haircut
makes cashing out correct — and that happens constantly (the true count is the wrong summary: what matters is the
hand-specific composition). `nn_v1` cashes out in 16.5 % of play decisions (21 per 100 rounds), exactly as often
as the solver oracle (16.4 %), gaining **+0.020 units per cash-out** over the best way to keep playing (solver
estimate; one realised counterfactual hold round per cash-out confirms it: hold −0.222 vs cash-out −0.195).

| hand class | decisions /1000 rounds | cash-out rate | mean TC at cash-out | gain per cash-out |
|---|---|---|---|---|
| hard 12–16 v 7–A | 221 | 25.8 % | **+1.5** | +0.019 |
| hard 12–16 v 2–6 | 151 | 20.0 % | **−1.5** | +0.021 |
| hard ≤ 11 (double hands) | 196 | 13.1 % | −1.3 | +0.035 |
| hard 17–21 | 157 | 15.9 % | −0.2 | +0.017 |
| soft 2-card | 95 | 12.7 % | +0.8 | +0.017 |
| pairs | 142 | 8.3 % | +0.1 | +0.020 |
| 3+ cards | 318 | 15.3 % | +0.4 | +0.015 |

Cash-out rate by Hi-Lo TC: 9.5 % at TC 0, rising to 25–33 % at |TC| ≥ 3 — stiff hands against a ten are cashed out
in *rich* shoes (more tens: the dealer makes more 20s and hitting busts more), double-down hands and stiff hands
against small cards in *poor* shoes (the double / the dealer bust loses value). In a neutral shoe it is rare and
the network keeps playing (e.g. soft 17 v A at TC −0.1, early shoe: Q(hit) −0.179 > cash-out −0.192; an early
MC-trained checkpoint, `nn:med`, wrongly cashed this out — see §2.1).

### 4.3 ⚠ The cash-out edge rests on a modelling assumption

The engine prices offers on a fresh shoe (docs/RULES.md §1, §5 item 3), as the official help suggests ("recalculated
from hand value, dealer up card and your decisions"; RTP 98 %). If Pragmatic's live offers also depend on the
cards already seen — or on the exact cards in the hand — most of the +0.48 % from cashing out disappears; the
composition-play edge (+0.14 %), the bet-sizing edge and the side-bet edges do not depend on it. The evaluation
always reports both (`nn_v1:flat` vs `nn_v1:flat_nocash`, `solver` vs `solver_nocash`). Compare these fresh-shoe
offers for a €1 bet with the live game before trusting the cash-out edge:

| hand | fair value | offer (€1 bet) | EV of cashing out | haircut (EV units) |
|---|---|---|---|---|
| 16 v T (T,6) | 0.4248 | €0.42 | −0.584 | 0.0085 |
| 15 v T (T,5) | 0.4575 | €0.45 | −0.552 | 0.0091 |
| 12 v 2 (T,2) | 0.7466 | €0.73 | −0.268 | 0.0149 |
| 11 v 6 (6,5) | 1.6674 | €1.63 | +0.634 | 0.0333 |
| 20 v T (T,T) | 1.4350 | €1.41 | +0.406 | 0.0287 |
| A,7 v 9 | 0.9010 | €0.88 | −0.117 | 0.0180 |
| 12 v T, 3 cards | 0.5883 | €0.58 | −0.424 | 0.0118 |

(Offers are rounded to the cent in the engine; with larger bets the offer is `round(0.98 × fair × bet, 2)`.)

### 4.4 Bet head vs exact analytics

20,000 pre-deal states of natural shoes (`docs/nn_eval.md`):

| output | mean predicted | mean exact | corr | MAE | P(pred > 0) | P(exact > 0) |
|---|---|---|---|---|---|---|
| main (vs EoR estimate for *basic* play) | +0.0003 | −0.0038 | 0.864 | 0.0045 | 38.4 % | 29.8 % |
| Perfect Pairs | −0.0410 | −0.0402 | 0.675 | 0.0072 | 1.3 % | 2.3 % |
| 21+3 | −0.0365 | −0.0371 | 0.721 | 0.0071 | 1.7 % | 2.6 % |
| Crazy 7 | −0.0559 | −0.0575 | **0.993** | 0.0179 | 33.9 % | 33.7 % |
| Bust Bonus | −0.0567 | −0.0564 | 0.981 | 0.0078 | 12.9 % | 12.6 % |
| insurance (if an ace shows) | −0.0760 | −0.0760 | **0.999** | 0.0019 | 9.5 % | 8.8 % |

* Learned from realised returns only, the bet head reproduces the exact EVs of Crazy 7, Bust Bonus and insurance
  almost perfectly. Perfect Pairs and 21+3 are weaker (r ≈ 0.7): they depend on suits and on the ranks *inside*
  the ten bucket (J/Q/K pairs), which the bucket features cannot express — an obvious feature to add.
* `main` is +0.4 % above the basic-strategy estimate because it predicts the EV **under the network's own play**
  (cash-outs and deviations). It is still ~0.15 % *below* the network's realised flat EV (+0.20 %), because one
  third of the main-bet targets come from generation 0, played by basic strategy — so Kelly bets are slightly too
  small. Fix: train the main output only on on-policy rows (a cheap improvement, §7).

## 5. Side bets and Crazy 7 — how often are they +EV?

`uv run python -m onebj.ai.sidebet_study --shoes 4000` computes, before every round of 4,000 simulated shoes
(basic strategy, crowd on), the **exact** EV of each side bet for the coming round from the unseen composition
(`onebj.analytics`; raw output `checkpoints/sidebet_study.json`). Two-halves (Napoleon) shoe, ~52 rounds per shoe:

| bet | mean EV | 5th–95th pct | P(EV > 0) | P(EV > 5 %) | mean EV when > 0 | shoes with a +EV round | +EV rounds / shoe | € per 100 rounds (€1 when +EV) |
|---|---|---|---|---|---|---|---|---|
| Perfect Pairs | −4.11 % | −6.5 … −1.6 % | 2.1 % | 0.2 % | +2.0 % | 24 % | 1.1 | €0.04 |
| 21+3 | −3.72 % | −6.1 … −1.0 % | 2.8 % | 0.3 % | +2.1 % | 27 % | 1.5 | €0.06 |
| **Crazy 7** | −5.85 % | **−46 … +39 %** | **33.6 %** | 25.1 % | **+20.4 %** | 85 % | 17.4 | **€6.85** |
| Bust Bonus | −5.76 % | −14.1 … +3.1 % | 10.6 % | 3.2 % | +4.3 % | 49 % | 5.5 | €0.45 |
| insurance (if an ace shows) | −7.78 % | −18.2 … +2.7 % | 8.3 % | 3.0 % | +4.9 % | 43 % | 4.3 | €0.03 |

(A plain single 8-deck shoe dealt to 75 % gives nearly the same numbers: Crazy 7 +EV in 34.6 % of rounds, €7.01
per 100 rounds — the two-halves procedure barely matters because the count carries over the half switch.)

**Crazy 7 is extremely sensitive to the number of 7s left** (official rule: the player's first three cards; the
2000:1 / 500:1 three-seven tiers dominate the EV):

EV by number of 7s left (other ranks at their expected share):

* 312 unseen cards (expected 24 sevens): 18 → −43 %, 21 → −26 %, **24 → −7.0 %**, 27 → +15.5 %, 30 → +41 %, 33 → +71 %
* 208 unseen (expected 16): 12 → −45 %, 14 → −29 %, **16 → −10.5 %**, 18 → +11 %, 20 → +36 %, 22 → +65 %
* 104 unseen, end of half 2 (expected 8): 6 → −52 %, 7 → −37 %, **8 → −20 %**, 9 → −0.6 %, 10 → +22 %, 11 → +49 %

(At the expected proportion the EV *falls* as the shoe gets smaller: drawing three 7s without replacement from a
small pool is rarer. Deep in the shoe, the swings dominate.)

A third more or fewer sevens than expected is normal in an 8-deck shoe, so the EV swings between −46 % and +39 %
(5th–95th percentile) and is positive a third of the time. The mock's "huge +EV in 7-rich spots" is real, and
frequent. Confirmed by realised play in the engine (2M rounds, `docs/nn_eval.md`):

| agent | Crazy 7 bets | realised RTP | ± SE | Bust Bonus bets | RTP | PP / 21+3 |
|---|---|---|---|---|---|---|
| `nn_v1` (bet head, EV > 2 %) | 627,286 (31 % of rounds) | **121.5 %** | 2.1 % | 136,774 | 108.8 % ± 1.1 % | ~101 % on 8–11k bets |
| `hilo` (exact analytic EV > 0) | 698,405 | 116.3 % | 2.0 % | 208,425 | 105.1 % ± 0.9 % | ~102.5 % on 42–55k bets |

The network's side-bet selection *beats* betting on exact EV > 0 (it uses a 2 % margin, which skips the marginal
spots whose EV is eaten by the without-replacement effects).

**What it is worth, honestly.** Crazy 7 contributes +0.070 units per round to `nn_v1` (Bust Bonus +0.014,
PP/21+3 ~0) — more than the whole main-game edge with bet spreading (+0.032). But:
* The standard deviation is enormous (≈ 14 per unit staked; `nn_v1`'s σ per round jumps from 3.1 to 11.3 units).
  Kelly allows ≈ €1 per €1000 of bankroll, so €1 stakes are only sensible with a ≥ €1000 bankroll, and the value is
  ~€7 per 100 rounds at €1 — i.e. a few euros per hour at a live table. It scales linearly with the bankroll (stakes
  up to €500), not with the main-bet unit.
* It requires counting the **7s** (Hi-Lo ignores them) — the network uses the per-rank `unseen_7` input.
* It depends on the Crazy 7 rule as modelled: the player's third card is the shared hand's third card (your hit,
  or the crowd's) — docs/RULES.md §5 item 4. If only a card you take yourself counted, you would still get it by
  hitting/splitting 7-7 (basic strategy always does), so the edge would mostly survive.
* PP and 21+3 are practically never worth it (+EV in 2–3 % of rounds by ~2 %); Bust Bonus is a modest edge
  (+EV in 11 % of rounds, ~+4 %); insurance is +EV in 8 % of ace-up rounds (the network insures at TC ≈ +4,
  realised +5.0 % on 48.6k units insured).

## 6. Engine changes, tests and caveats

* **Engine bug fixed** (reported by integration testing): `onebj.sim.Metrics` counted every cashed-out hand as a
  win. It now classifies a cash-out by payout vs stake (win / loss / push), and counts `cashouts` and
  `cashout_net` (also in `to_dict`). Test: `backend/tests/test_ai_metrics.py`. No other engine file was changed;
  `CashSolver` extends the engine solver by subclassing in `ai/oracle.py`.
* No engine rule bugs found. Cross-checks that passed: the deal-Monte-Carlo side-bet returns (engine `settle_*`)
  match `onebj.analytics` exactly (test); realised side-bet RTPs of the agents match the exact-EV study; the
  realised counterfactual hold returns agree with the solver's hold EVs within 0.006 in cash-out states; and the
  realised flat-bet EV of the solver oracle (+0.645 % vs basic) is what its regret predicts.
* Tests (`uv run pytest backend/tests/test_ai*.py`, ~15 s): feature names/size, Observation vs fast-path vectors
  identical, features independent of the hole card, NumPy mirror == torch, legality (never an illegal action),
  fast path == Observation path, bet sizing, trace schema vs SPEC §5 / `frontend/src/protocol.ts`, describe()
  schema, deterministic load + play, `list_checkpoints` / training log, deal Monte Carlo vs exact EVs, generator
  shapes/masks for all target modes, `CashSolver`, a tiny end-to-end training and the `--quick` CLI.
* Reproducibility, measured: the default run reproduced every logged number exactly when re-run.
* Caveats: (1) the cash-out edge rests on composition-blind offers (§4.3); (2) the play head imitates an
  infinite-deck DP — the engine-measured gap to that DP is small (0.02 % per round) but the DP itself is not exactly
  optimal for the finite shoe; (3) EV numbers are per €1 minimum unit with a fixed €1000 Kelly bankroll — in the
  live app (bankroll enforced, `strict=True`) bets are additionally capped by the balance.

## 7. Retraining and improving it

```bash
uv run python -m onebj.ai.train --name nn_v1                       # default: ~14 min on an M4 (10 cores)
uv run python -m onebj.ai.train --name smoke --quick               # ~10 s sanity run
uv run python -m onebj.ai.train --name nn_v2 --config my.json      # any subset of TrainConfig (JSON)
uv run python -m onebj.ai.train --name big --scale 2 --steps 120000 --generations 4
uv run python -m onebj.ai.train --name nocash --game-patch '{"rules": {"cashout": false}}' --out checkpoints/ablations
uv run python -m onebj.ai.train --name nn_v1_ft --init nn_v1       # warm start from a checkpoint
uv run python -m onebj.ai.evaluate --agents nn_v2,nn_v2:flat,nn_v2:flat_nocash,basic,hilo_nosides,hilo \
    --rounds 2000000 --duplicate 2000000 --dup-solver --analysis --save-metrics --markdown docs/nn_eval.md
uv run python -m onebj.ai.sidebet_study --shoes 4000               # exact side-bet +EV frequencies
uv run pytest backend/tests/test_ai*.py                            # ~15 s incl. a tiny end-to-end training
```

Every run writes `checkpoints/<name>.pt/.json` plus per-generation snapshots in `checkpoints/<name>_generations/`
(not listed by the server). The server lists every top-level checkpoint as `nn:<name>`; keep experiments elsewhere
with `--out`.

| knob (`TrainConfig` / `gen`) | default | what it does / what to try |
|---|---|---|
| `trunk` | `[128, 64]` | width. `[256, 128]` halves the solver regret (see `nn_v1_large`) at the cost of a busier graph |
| `generations`, `steps_per_generation` | 4M+3M+3M play, 1.5M bet each; 20k/15k/25k steps | more data and steps keep helping a little; regret 0.00043 → 0.00036 from gen 0 to gen 2 |
| `targets_per_generation` | solver ×3 | `"blend"` (+`gen.mc_weight`) mixes engine rollouts into the targets; `"mc"` is pure Monte Carlo (needs ~10–20× the data) |
| `gen.k_play`, `gen.k_bet` | 2, 4 | rollouts per state for MC/blend targets, full rounds per bet state |
| `gen.deal_groups` | 2 | unseen-pool permutations per bet state for the PP/21+3/Crazy 7 deal Monte Carlo |
| `gen.epsilon`, `gen.p_tilt`, `gen.tilt_max` | 0.10, 0.5, 0.08 | exploration and shoe skew (state coverage) |
| `bet_loss_weight` | 0.5 | balance of the two heads on the shared trunk |
| `lr`, `lr_min`, `lr_decay_per_generation`, `batch_size` | 2e-3, 2e-5, 0.5, 4096 | cosine cycle per generation |
| `feature_spec` | see §1.1 | e.g. a wider/narrower total one-hot; add features in `features.py` (bump `FeatureSpec.version`) |
| `bet` (`BetConfig`) | ½ Kelly, 1–12 units, side threshold 2 % | sizing only — change at load time without retraining: `NNAgent.load("nn_v1", cfg, bet={"unit": 10})` |

Ideas that should pay off, roughly in order: a wider trunk or a separate small bet tower (the shared trunk costs the
play head a little); adding suit and rank-within-ten composition features (Perfect Pairs / 21+3 depend on them, the
bucket features can't express it); an exact finite-deck correction of the solver targets instead of the noisy
rollout blend (e.g. MC with control variates on the dealer outcome); learning the bet sizing end-to-end against
risk of ruin instead of fixed ½ Kelly; and checking the cash-out model against the live game (§4.3).
